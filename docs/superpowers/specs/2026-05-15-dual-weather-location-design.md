# 双人天气与位置系统设计

## 目标

在现有首页天气卡片基础上，扩展为“绑定双方各自独立的天气与位置展示”。

最终效果：

- 首页同时显示“我”和“对方”的天气
- 位置展示粒度为“城市 + 区县”
- 优先使用实时定位
- 定位失败或用户未授权时，自动回退到手动设置的位置
- 天气结果按 1 小时缓存，首页优先秒开，再按需刷新

## 当前现状

现有实现主要集中在以下文件：

- `utils/weather.js`
- `utils/storage.js`
- `pages/index/index.js`
- `pages/index/index.wxml`

当前问题：

1. 天气系统只获取当前设备的一份天气
2. 首页虽然有“双方天气”的 UI 区块，但两边都在复用同一份天气数据
3. 项目里还没有双方独立的位置档案和天气快照结构
4. 位置获取失败时，只会降级到本地模拟天气，不能回退到用户手动设置的位置

## 设计原则

### 1. 双方数据独立

“我”和“对方”的天气不能共享同一份结果。

每个绑定角色都应拥有：

- 自己的位置配置
- 自己的天气快照
- 自己的更新时间

### 2. 实时定位优先，手动设置兜底

天气位置来源分成两种：

- `auto`：自动定位
- `manual`：手动设置

刷新逻辑：

1. 优先尝试自动定位
2. 自动定位成功，则更新当前位置和天气
3. 自动定位失败，则回退到手动设置的位置
4. 如果手动位置也不存在，再降级为当前项目已有的本地模拟天气

### 3. 持久化与展示分层

位置配置和天气快照属于业务数据，应存入共享云端文档。

首页展示时：

- 当前用户自己的天气允许主动刷新
- 对方天气只展示对方最近一次同步结果

也就是说：

- 我负责更新“我的天气”
- 对方负责更新“对方的天气”

这样可以避免一台设备代替另一方定位。

### 4. 首页优先秒开

缓存策略：

- 读取本地或云端已同步的天气快照立即展示
- 如果当前用户自己的天气快照已超过 1 小时，则后台刷新
- 对方天气不在本设备主动重新请求，只等对方设备自己同步

## 数据模型

在情侣共享文档中新增以下字段：

### 位置档案

- `devWeatherProfile`
- `userWeatherProfile`

结构建议：

```js
{
  mode: 'auto' | 'manual',
  province: '浙江省',
  city: '杭州市',
  district: '西湖区',
  locationId: '101210106',
  displayName: '杭州市 西湖区',
  lat: 30.25,
  lon: 120.13,
  updatedAt: 1710000000000
}
```

字段说明：

- `mode`：当前使用的定位模式
- `province/city/district`：用于显示和调试
- `locationId`：和风天气查询 ID，后续天气接口直接复用
- `displayName`：首页显示文本，建议统一为“城市 区县”
- `lat/lon`：用于定位成功后的记录
- `updatedAt`：档案更新时间

### 天气快照

- `devWeatherSnapshot`
- `userWeatherSnapshot`

结构建议：

```js
{
  temp: 26,
  minTemp: 23,
  maxTemp: 29,
  text: '多云',
  icon: '⛅',
  clothing: '温度舒适，穿件短袖或裙子就很好～',
  clothingIcon: '🧺',
  location: '杭州市 西湖区',
  source: 'auto' | 'manual' | 'fallback',
  updatedAt: 1710000000000
}
```

字段说明：

- `source`：本次天气来源
  - `auto`：来自实时定位
  - `manual`：来自手动设置位置
  - `fallback`：来自本地模拟天气

## 本地存储设计

本地不额外引入复杂结构，只做两类缓存：

1. 共享文档同步回来的 profile / snapshot 数据
2. 当前设备天气刷新过程中需要的短期缓存

建议在 `utils/storage.js` 中新增映射字段，使其进入云同步体系：

- `my_weather_profile`
- `partner_weather_profile`
- `my_weather_snapshot`
- `partner_weather_snapshot`

实际云端字段根据角色映射到：

- `devWeatherProfile` / `userWeatherProfile`
- `devWeatherSnapshot` / `userWeatherSnapshot`

这样现有“角色感知字段映射”模式可以延续，不需要另起一套权限系统。

## 模块改造方案

### 1. `utils/weather.js`

职责从“只查当前设备一份天气”扩展为“支持双人天气的数据组装”。

建议拆出以下能力：

- 获取当前位置
- 根据经纬度查询城市和区县信息
- 根据 `locationId` 查询实时天气
- 基于实时定位生成 profile + snapshot
- 基于手动位置生成 snapshot
- 基于 fallback 生成 snapshot
- 汇总首页双人天气展示对象

建议新增或重构为以下接口：

- `refreshMyWeather()`
  - 刷新当前用户自己的 profile + snapshot
  - 内部执行“自动定位优先，手动位置兜底”
  - 成功后写入 storage 并同步云端

- `getWeatherDisplayData()`
  - 读取当前双方的 snapshot
  - 组装首页使用的数据结构

- `resolveManualLocation(locationInput)`
  - 将用户手动选择的省/市/区县转换成 `locationId`

### 2. `utils/storage.js`

需要扩展：

- 新增 weather profile / snapshot 的 storage key
- 新增角色感知字段映射
- 增加 getter / setter
- 接入现有云同步机制

注意点：

- 这些字段属于普通业务数据，不涉及临时 URL 之类的特殊转换
- 但要避免因为页面重复 setData 导致高频云同步

### 3. `pages/index/index.js`

首页刷新逻辑需要从“加载一份 weather”改为“双人天气展示 + 我的天气按需刷新”。

建议流程：

1. 页面进入时，先读取已同步好的双方 snapshot
2. 立即渲染首页天气卡片
3. 检查“我的天气”是否超过 1 小时
4. 如果过期，则后台调用 `weather.refreshMyWeather()`
5. 刷新成功后重新读取 display data 并更新页面

对方天气：

- 只展示云端同步来的对方快照
- 不在当前设备主动请求对方定位和天气

### 4. `pages/index/index.wxml`

首页天气卡片要改成真正的双人展示。

建议结构：

- 卡片顶部：主提示文案，例如“今天天气”
- 中间：左右两列
  - 我：名字、区县、天气图标、温度、天气描述
  - 对方：名字、区县、天气图标、温度、天气描述
- 底部：
  - 当前用户的穿衣建议
  - 或者统一提示“根据你的位置给出穿衣建议”

如果只有一方有数据：

- 另一方显示“等待 TA 更新位置”

如果双方都没有数据：

- 降级显示当前已有的 fallback 天气卡片

### 5. `pages/profile/profile.js`

资料页建议增加“我的天气位置设置”入口。

需要提供两个操作：

1. `使用当前位置`
2. `手动设置位置`

手动设置建议使用微信已有的地区选择器或省市区级联选择。

资料页显示建议包含：

- 当前模式：自动 / 手动
- 当前位置：城市 + 区县
- 上次更新时间

## 用户流程

### 首次使用

1. 用户进入首页
2. 首页尝试刷新我的天气
3. 若定位成功：
   - 保存我的自动定位 profile
   - 保存我的实时天气 snapshot
4. 若定位失败：
   - 检查是否存在手动位置
   - 有则按手动位置查天气
   - 没有则使用 fallback 天气

### 日常刷新

1. 用户进入首页
2. 直接展示双方现有 snapshot
3. 如果我的 snapshot 超过 1 小时：
   - 后台刷新我的天气
   - 刷新成功后同步云端
4. 对方下次打开小程序时，会按同样逻辑更新 TA 自己的天气

### 用户手动设置位置

1. 用户进入资料页
2. 选择手动设置位置
3. 选择省 / 市 / 区县
4. 系统解析 `locationId`
5. 保存为我的 `WeatherProfile`
6. 可立即触发一次天气刷新

## 异常与降级策略

### 定位失败

表现：

- 不弹阻塞式错误
- 首页继续显示已有缓存
- 如果没有缓存，则用 fallback 天气

提示文案：

- “未获取到当前位置，已切换为手动位置”
- “未获取到当前位置，当前显示默认天气”

### 手动位置配置无效

例如：

- 区县名称无法解析
- `locationId` 过期或接口失败

处理方式：

- 保留旧的手动位置
- 不清空已有天气快照
- 给出轻提示“位置解析失败，请重新选择”

### 对方没有上传过位置

首页展示：

- 名字正常显示
- 位置显示“等待 TA 设置位置”
- 天气显示“暂未同步”

## 权限与隐私边界

这次设计会同步双方的区县位置，因此属于比“城市级”更细的隐私数据。

边界约束：

1. 只同步到情侣共享文档，不额外上传到第三方业务库
2. 首页只显示城市 + 区县，不展示经纬度
3. 经纬度只用于天气解析和 profile 记录，不在 UI 上暴露
4. 允许用户切换为手动位置，避免始终暴露实时位置

## 测试策略

至少覆盖以下场景：

1. 自动定位成功，首页展示我的区县和天气
2. 自动定位失败，但已有手动位置，能正确回退
3. 自动定位失败且没有手动位置，能正确 fallback
4. 双方已有独立快照时，首页能同时展示双方天气
5. 我的天气过期后，进入首页会刷新
6. 对方天气不过期时，不会被我这边覆盖
7. 手动改位置后，新的区县和天气能同步给对方

## 实现建议

按最小风险顺序分三步做：

1. 先补 storage 数据结构与 weather 工具函数
2. 再接首页展示和刷新逻辑
3. 最后补资料页的手动位置设置入口

这样即使第三步还没做完，前两步也能先让“双人自动天气同步”跑起来。

## 结论

这次需求本质上不是“把单人天气复制成两份”，而是要建立一套：

- 双方独立的位置档案
- 双方独立的天气快照
- 自动定位优先、手动位置兜底
- 1 小时缓存刷新

如果后续实现严格按这个边界来做，首页天气展示、同步时机和失败兜底都会比较清晰，也不容易和现有存储架构打架。
